# AI测试用例生成规范

## 📋 规范概述

本规范用于指导AI基于**知识库**直接生成**YAML格式测试用例**和**测试用例集总览文件**。

**核心原则**:
- ✅ 直接从知识库生成，无需中间层
- ✅ 同时生成YAML用例和MD总览文件
- ✅ 确保生成的用例可直接执行
- ✅ 确保总览文件业务友好

---

## 🎯 生成流程

```
输入：业务流程知识文件（TKF_xxx.md）
    ↓
步骤1：分析知识库结构
    ↓
步骤2：从业务场景中识别测试场景
    ↓
步骤3：为每个测试场景生成YAML用例
    ↓
步骤4：生成MD总览文件
    ↓
输出：N个YAML用例 + 1个MD总览
```

**关键**: AI需要自动从业务流程知识中识别所有需要测试的场景，而不是由人工提供场景列表。

---

## 📚 输入要求

### 唯一输入：知识库

**用户指令示例**:
```
请基于知识库中的 TKF_001_离线剧本批量生成.md 生成覆盖本流程的全部测试用例，用例格式为可执行的YAML格式
```

**知识库结构**:
```
ai_test_knowledge/BIZ_REQ_<需求ID>_<需求名称>/
├── flows/
│   └── TKF_<流程ID>_<流程名称>.md          # 业务流程知识（核心输入）
├── components/
│   ├── TKD_<数据ID>_<数据组件名称>.md      # 数据组件知识
│   ├── TKJ_<JobID>_<Job名称>.md           # Job组件知识
│   └── TKI_<集成ID>_<集成组件名称>.md      # 集成组件知识
└── rules/
    └── TKR_<规则ID>_<规则名称>.md          # 业务规则知识
```

**知识文件必须包含的信息**:

**业务流程文件** (TKF_xxx.md) - **核心输入**:
- ✅ 业务步骤详细说明
- ✅ 涉及的组件列表（Job、数据、集成）
- ✅ 涉及的业务规则列表
- ✅ **业务场景描述**（AI从这里提取测试场景）
- ✅ 数据流转关系

**重要**: 业务流程文件中的"业务场景"部分是AI自动识别测试场景的关键！

**示例** (来自TKF_001_离线剧本批量生成.md):
```markdown
## 业务场景

### 场景1：正常批量生成
**业务描述**：为一批案件生成剧本
**前置条件**：
- DataHub中有待处理的案件数据
- 案件数据已通过质量检查
**业务步骤**：
1. 拉取名单：获取案件列表
2. 生成剧本：为每个案件生成剧本
**预期结果**：
- 所有案件都生成了剧本
- 剧本内容符合业务要求

### 场景2：断点续传
**业务描述**：Job执行失败后，从上次位置继续
**前置条件**：
- 上次Job执行到一半失败了
- 已处理部分案件的记录存在
**业务步骤**：
1. 重新触发拉取名单Job
2. Job自动从上次位置继续
3. 生成剩余案件的剧本
**预期结果**：
- 不重复处理已完成的案件
- 只处理剩余的案件
```

**数据组件文件** (TKD_xxx.md):
- ✅ 表结构定义（CREATE TABLE语句）
- ✅ 字段说明和测试值示例
- ✅ 测试数据模板（minimal_valid、complete、failure）
- ✅ 常用查询SQL
- ✅ 关键知识点（JSON处理、异步等待、字段映射等）

**Job组件文件** (TKJ_xxx.md):
- ✅ 输入参数规范
- ✅ 执行逻辑说明
- ✅ 输出结果说明
- ✅ 触发方式示例
- ✅ 结果验证示例

**业务规则文件** (TKR_xxx.md):
- ✅ 规则定义
- ✅ 规则条件
- ✅ 规则验证方式

## 📝 输出要求

### 输出1：YAML格式测试用例

**文件命名**: `TC_<业务流程ID>_<序号>_<用例名称>.yaml`

**示例**: `TC_TKF001_001_离线剧本批量生成_正常流程.yaml`

**文件结构**: 参考 `ai_test_framework/docs/YAML格式测试用例生成规范.md`

**关键要求**:
- ✅ 包含完整的文件头注释（知识来源、生成方式、生成时间）
- ✅ 包含所有必需字段（test_case_id、test_name、business_flow等）
- ✅ 包含详细的related_knowledge（flows、rules、data_components等）
- ✅ preconditions必须先清理后准备
- ✅ test_steps必须包含intent说明
- ✅ assertions必须包含timeout和poll_interval（异步操作）
- ✅ 每个步骤都有详细的注释说明

### 输出2：MD格式测试用例集总览

**文件命名**: `<业务流程ID>_测试用例集总览.md`

**示例**: `TKF001_测试用例集总览.md`

**文件结构**:
```markdown
# <业务流程ID> <业务流程名称> - 测试用例集总览

## 📋 业务流程
## 🎯 测试覆盖策略
## 📊 测试用例清单
## 📈 测试覆盖率统计
## 🚀 执行建议
```

**关键要求**:
- ✅ 业务友好，非技术人员可读
- ✅ 包含测试覆盖策略（场景、规则、组件）
- ✅ 每个用例包含：优先级、测试类型、测试目标、关键验证点
- ✅ 包含覆盖率统计
- ✅ 包含执行建议

## 🔍 生成步骤详解

### 步骤1：分析知识库结构

**任务**: 读取并理解知识库中的所有文件

**操作**:



1. 读取业务流程文件（TKF_xxx.md）
2. 读取所有关联的数据组件文件（TKD_xxx.md）
3. 读取所有关联的Job组件文件（TKJ_xxx.md）
4. 读取所有关联的集成组件文件（TKI_xxx.md）
5. 读取所有关联的业务规则文件（TKR_xxx.md）

**提取的关键信息**:
- 业务流程ID和名称
- 业务步骤列表
- 组件列表（Job、数据、集成）
- 业务规则列表
- 数据表结构和字段
- 测试数据模板
- 关键知识点（超时时间、字段映射等）

---

### 步骤2：从业务场景中识别测试场景

**任务**: 从业务流程知识中自动识别所有需要测试的场景

**2.1 读取业务场景部分**

从 `TKF_xxx.md` 的"业务场景"部分提取所有场景：

```markdown
## 业务场景

### 场景1：正常批量生成
### 场景2：断点续传
### 场景3：失败重试（隐含）
### 场景4：处理中补偿（隐含）
### 场景5：异常场景（隐含）
```

**2.2 识别测试场景类型**

基于业务场景和业务规则，AI需要自动识别以下测试场景类型：

**正常场景**:
- 从业务场景中明确描述的正常流程
- 示例：场景1（正常批量生成）

**异常场景**:
- 从业务规则中推导的异常情况
- 示例：TKR_001规则 → DP数据未产出场景

**容错场景**:
- 从业务场景中描述的容错机制
- 示例：场景2（断点续传）

**补偿场景**:
- 从业务规则和状态流转中推导
- 示例：TKR_003规则 + 状态流转图 → FAILURE重试、PROCESSING补偿

**2.3 提取业务流程步骤**

从 `TKF_xxx.md` 中提取：
```yaml
业务步骤:
  步骤1: 拉取名单
    - 执行组件: TKJ_001
    - 业务规则: TKR_001, TKR_002

  步骤2: 生成剧本
    - 执行组件: TKJ_002
    - 业务规则: TKR_003
```

**2.4 提取原语映射**

从 `TKJ_xxx.md` 中提取触发方式：
```yaml
步骤1（拉取名单）→ 原语映射:
  primitive: trigger_scheduled_job
  params:
    job_name: "AiScriptUidPullJob"
    external_data:
      source: "postLoan"
```

**2.5 提取测试数据模板**

从 `TKD_xxx.md` 中提取测试数据模板：
```yaml
用户数据模板（TKD_003）:
  minimal_valid:
    customerName: "张三"
    age: "30"
    sex: "男"
    # ... 其他必填字段
```

**2.6 提取断言验证**

从 `TKJ_xxx.md` 和 `TKD_xxx.md` 中提取结果验证方式：
```yaml
验证Job执行成功:
  primitive: assert_field_equals
  params:
    table: "copilot.common_job_status"
    field: "status"
    where: "job_name='AiScriptUidPullJob' AND business_type='postLoan' ORDER BY id DESC LIMIT 1"
    expected: "SUCCESS"
    timeout: 30
    poll_interval: 2
```

**2.7 提取关键知识点**

从 `TKD_xxx.md` 的"关键知识点"部分提取：
- 异步等待时间（timeout参数）
- 字段映射关系（source vs business_type）
- JSON字段处理（JSON_UNQUOTE）
- 数据准备顺序（先清理后准备）

### 步骤3：为每个测试场景生成YAML用例

**任务**: 为步骤2识别的每个测试场景生成一个完整的YAML测试用例

**重要**:
- 一个业务流程 → 多个测试场景 → 多个YAML用例
- 每个场景对应一个独立的YAML文件
- 用例编号按顺序递增（001, 002, 003...）

**3.1 生成文件头注释**

```yaml
# ============================================================================
# 测试用例：<用例名称>
# ============================================================================
# 知识来源: <业务流程文件名>
# 生成方式: AI基于Test Knowledge Tree自动生成
# 生成时间: <当前日期>
# ============================================================================
```

**3.2 生成基本信息**

```yaml
test_case_id: TC_<业务流程ID>_<序号>
test_name: <业务流程名称>_<场景名称>
business_flow: <业务流程ID>
priority: <P0/P1/P2>  # 根据场景识别规则自动判定
automation_level: <L0/L1/L2/L3>  # 根据知识库完整性自动判定
business_rules:
  - <规则ID1>  # <规则名称>
  - <规则ID2>  # <规则名称>
```

**3.3 生成关联知识**

```yaml
related_knowledge:
  flows:
    - <流程文件名>
  rules:
    - <规则文件名1>
    - <规则文件名2>
  data_components:
    - <数据组件文件名1>
    - <数据组件文件名2>
  job_components:
    - <Job组件文件名1>
    - <Job组件文件名2>
  integration_components:
    - <集成组件文件名>
```

**3.4 生成前置条件**

**重要**: 必须先清理后准备！

```yaml
test_intent:
  preconditions:
    # 前置1: 清空历史数据
    - intent: "清空历史测试数据，确保测试环境干净"
      primitive: clean_test_data
      params:
        source: "<业务来源>"
        tables:
          # 按照从下游到上游的顺序清理
          - "<下游表1>"
          - "<下游表2>"
          - "<中游表1>"
          # 配置表不清理

    # 前置2: 准备测试数据
    - intent: "准备DataHub数据"
      primitive: prepare_datahub_data
      params:
        source: "<业务来源>"
        batch_status: "1"  # 根据场景调整
        users:
          # 使用测试数据模板
          - <用户数据1>
          - <用户数据2>
```

**3.5 生成测试步骤**

```yaml
  test_steps:
    # 步骤1: 触发Job
    - intent: "<业务步骤描述>"
      primitive: trigger_scheduled_job
      params:
        job_name: "<Job名称>"
        external_data:
          <参数1>: <值1>

      # 断言: 验证Job执行成功
      assertions:
        - intent: "验证Job执行成功"
          primitive: assert_field_equals
          params:
            table: "<表名>"
            field: "<字段名>"
            where: "<查询条件>"
            expected: "<期望值>"
            timeout: <超时时间>
            poll_interval: <轮询间隔>
```

**3.6 生成预期结果**

```yaml
expected_result: |
  <业务友好的预期结果描述>
  - 验证点1
  - 验证点2
  - 验证点3
```

**3.7 添加详细注释**

在每个关键位置添加注释：
- 知识来源（哪个文件）
- 参数说明（为什么这样设置）
- 注意事项（常见错误）
- 数据流转（数据如何流动）

## 🎯 测试场景识别规则

### 如何从业务流程知识中自动识别测试场景

**输入**: 业务流程文件（TKF_xxx.md）

**输出**: 完整的测试场景列表

### 识别规则

#### 规则1：明确描述的业务场景 → 直接转换为测试场景

**来源**: 业务流程文件的"业务场景"部分

**示例**:
```markdown
## 业务场景

### 场景1：正常批量生成
→ 测试场景1：正常批量生成（首次执行）

### 场景2：断点续传
→ 测试场景2：断点续传
```

#### 规则2：业务规则 → 推导异常测试场景

**来源**: 业务流程文件的"业务规则"部分

**示例**:
```markdown
业务规则:
- TKR_001：DP数据产出状态判断（batch_status = '1'）
→ 测试场景：DP数据未产出（batch_status != '1'）
```

#### 规则3：状态流转 → 推导状态相关测试场景

**来源**: 数据组件文件的"状态流转"部分

**示例**:
```markdown
状态流转:
INIT → PROCESSING → SUCCESS
INIT → PROCESSING → FAILURE
→ 测试场景1：FAILURE状态重试
→ 测试场景2：PROCESSING状态补偿（超时）
```

#### 规则4：Job断点续传规则 → 推导断点续传场景

**来源**: 业务规则文件（TKR_002）

**示例**:
```markdown
TKR_002：Job断点续传规则
→ 测试场景：断点续传（Job失败后继续）
```

### 完整示例：TKF_001的场景识别

**输入**: `TKF_001_离线剧本批量生成.md`

**分析过程**:

1. **读取业务场景部分**:
   - 场景1：正常批量生成 ✅
   - 场景2：断点续传 ✅

2. **读取业务规则部分**:
   - TKR_001：DP数据产出状态判断
     → 推导：DP数据未产出异常场景 ✅
   - TKR_002：Job断点续传规则
     → 已在场景2覆盖 ✓
   - TKR_003：剧本生成状态判断
     → 推导：需要测试不同状态 ✅

3. **读取数据组件的状态流转**:
   - TKD_001（日志表）状态流转：
     - INIT → PROCESSING → SUCCESS
     - INIT → PROCESSING → FAILURE
     → 推导：FAILURE重试场景 ✅
     → 推导：PROCESSING补偿场景 ✅

**输出**: 5个测试场景

| 场景ID | 场景名称 | 来源 | 优先级 |
|--------|---------|------|--------|
| 场景1 | 正常批量生成（首次执行） | 业务场景1 | P0 |
| 场景2 | 断点续传 | 业务场景2 + TKR_002 | P0 |
| 场景3 | 失败重试 | 状态流转 + TKR_003 | P1 |
| 场景4 | 处理中补偿 | 状态流转 + TKR_003 | P1 |
| 场景5 | DP数据未产出异常 | TKR_001 | P1 |

### 优先级判断规则

**P0（核心场景）**:
- 业务场景中明确描述的正常流程
- 业务场景中明确描述的核心容错机制（如断点续传）

**P1（重要场景）**:
- 从业务规则推导的异常场景
- 从状态流转推导的补偿场景

**P2（一般场景）**:
- 边界条件测试
- 性能测试

## 🎖️ 自动化等级标准

### 定义

**自动化等级**：表示AI生成的YAML测试用例可直接自动化执行的成熟度，基于知识库的完整性和清晰度自动判定。

### 等级划分

#### L3 - 高成熟可自动化 ⭐⭐⭐

**定义**: 知识完整清晰，AI可直接生成可运行的YAML用例，无需人工修改

**判定条件**（需同时满足）:
- ✅ 业务流程有明确的业务步骤说明
- ✅ Job组件有完整的触发方式示例（包含所有必需参数）
- ✅ Job组件有完整的结果验证示例（包含timeout/poll_interval）
- ✅ 数据组件有测试数据模板（minimal_valid或complete）
- ✅ 数据组件有关键知识点说明（超时时间、字段映射等）

## ⚠️ 关键注意事项

### 1. 数据准备顺序

**错误示例** ❌:
```yaml
preconditions:
  - intent: "准备数据"
    primitive: prepare_datahub_data
  - intent: "清理数据"
    primitive: clean_test_data  # 会把刚准备的数据清理掉！
```

**正确示例** ✅:
```yaml
preconditions:
  - intent: "清理数据"
    primitive: clean_test_data  # 先清理
  - intent: "准备数据"
    primitive: prepare_datahub_data  # 后准备
```

### 2. 异步等待时间

**所有Job执行的断言都必须使用timeout和poll_interval**：

```yaml
assertions:
  - primitive: assert_field_equals
    params:
      timeout: 30        # 必须设置
      poll_interval: 2   # 必须设置
```

**推荐timeout值**:
- Job1（名单拉取）：60-120秒
- Job2（剧本生成）：30-60秒

### 3. 字段映射差异

**注意**: `common_job_status`表使用`business_type`字段，其他表使用`source`字段

```yaml
# ✅ 正确：查询Job状态表
where: "job_name='AiScriptUidPullJob' AND business_type='postLoan'"

# ❌ 错误：使用source字段
where: "job_name='AiScriptUidPullJob' AND source='postLoan'"  # 字段不存在！
```

### 4. JSON字段处理

**必须使用JSON_UNQUOTE函数**：

```yaml
# ✅ 正确
field: "JSON_UNQUOTE(JSON_EXTRACT(output_data, '$.resp_code'))"

# ❌ 错误（返回带引号的字符串）
field: "JSON_EXTRACT(output_data, '$.resp_code')"
```

### 5. 批次号生成

**不要手动指定batch_no，让原语自动生成**：

```yaml
# ✅ 正确：不传batch_no，自动生成
params:
  source: "postLoan"
  batch_status: "1"

# ❌ 错误：手动指定batch_no
params:
  batch_no: "20260210001"  # 可能与其他测试冲突
```

## 💡 常见问题解答

### Q1: 如果业务流程文件中没有"业务场景"部分怎么办？

**A**: 从业务步骤中推导基本场景：
- 至少生成1个正常流程场景（覆盖所有业务步骤）
- 从业务规则推导异常场景
- 从状态流转推导补偿场景

### Q2: 如何判断场景的优先级？

**A**: 按照以下规则：
- **P0**: 业务场景中明确描述的正常流程和核心容错机制
- **P1**: 从规则和状态推导的异常/补偿场景
- **P2**: 边界条件和性能测试

### Q3: 如何确定测试数据的数量（如"2个用户"还是"4个用户"）？

**A**: 按照以下规则：
- **正常场景**: 2个用户（最小有效数据集）
- **断点续传**: 4个用户（模拟2页数据，每页2个）
- **失败重试/补偿**: 2条记录（验证批量处理）
- **异常场景**: 2个用户（验证异常处理逻辑）

### Q4: 如何确定timeout和poll_interval的值？

**A**: 从知识库的"关键知识点"部分获取：
- 如果知识库中有推荐值，使用推荐值
- 如果没有，使用默认值：
  - Job执行：timeout=60-120秒，poll_interval=5秒
  - 数据库操作：timeout=30秒，poll_interval=2-3秒

### Q5: 如何处理多个业务流程之间的依赖？

**A**:
- 每个业务流程独立生成测试用例
- 如果有依赖，在preconditions中准备依赖数据
- 不要跨流程引用测试用例

### Q6: 生成的用例数量是否有限制？

**A**:
- 建议每个业务流程生成3-10个测试用例
- 如果场景过多（>10个），考虑拆分业务流程
- 优先覆盖P0和P1场景
